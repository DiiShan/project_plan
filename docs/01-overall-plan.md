# 本地优先的个人项目工作台：总体规划

> 第一轮讨论结论归档。归档日期：2026-10-27。当前只归档规划，尚未开始开发。
>
> 本文保留第一轮总体规划及官方参考链接。当前第一阶段的范围、开发批次和完成标准，以后续的[第一阶段实施方案](02-phase-1-plan.md)为准。两轮关系见[仓库首页](../README.md)。本文中的 P0、P1 等是第一轮路线编号，不应与第二轮“第一阶段”及其六个批次机械等同。
>
> 本次上传没有重新开展技术核查。下面涉及的版本、支持期限及官方依据沿用原讨论；实施前需复核。所有性能数字都是待验证目标，不是已测量结果。文末只做 P0-A 窗口原型的提示保留为历史建议，当前首批实施应改用第二轮“可启动、可保存的最小应用”。

# 1. 方案摘要

## 1.1 明确结论

建议把它做成一个 **Windows 本地优先的“项目资产库＋工作上下文记录＋按需执行工具”**，而不是缩小版的企业项目管理平台。

它首先回答三个问题：

> **以前做过什么？这个项目现在是什么情况？下一次打开后，具体接着做什么？**

随后解决第四个问题：

> **已经做好的程序，怎样在明确授权、可观察、可停止的条件下反复使用？**

**主技术方案：C# + .NET 10 LTS + WPF + SQLite。**

采用一个桌面程序、一个本地数据库，按模块组织代码。不引入本地 HTTP 后端、数据库服务器、常驻 Python 服务、云账号系统或 AI 服务。

原讨论按 2026 年 10 月 27 日的官方支持政策选择 .NET 10 LTS：支持到 2028 年 11 月；.NET 8、9 将在 2026 年 11 月 10 日结束支持，因此这个新项目不建议从它们起步。WPF 是面向 Windows 的桌面界面框架，符合当前只解决 Windows 使用的范围。实施前应重新核查这些时间性信息。[.NET 官方支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

**唯一备选：Tauri 2 + TypeScript 前端 + Rust 本地核心。** 只有主方案的关键交互或维护成本经过实际验证不合适，或者以后明确要求复用 Web 界面时，才考虑切换；不能由 AI 编程工具自行换框架。

## 1.2 第一版到底得到什么

这里将“第一版”定义为下文的 **P1 管理 MVP**，而不是包含全部目标的版本。第二轮已将必要技术验证和这一管理 MVP 合并为当前第一阶段，实施以第二轮为准。

| 第一版必须得到 | 第一版暂不包含 |
|---|---|
| 一句话记录想法 | AI 自动摘要、语义搜索 |
| 少量字段登记项目，包括只有想法、对话、链接的项目 | 自动扫描和批量发现 |
| 按中文关键词、名称、用途、标签、类型、状态找回项目 | 自动判断项目是否值得复用 |
| 记录任务、下一步行动、计划日期、可选截止日期 | 完整日历、任务依赖、甘特图 |
| 记录“上次完成、当前阻塞、下次打开什么” | 自动读取开发工具内部历史 |
| 今日工作台和项目详情 | Windows 系统通知 |
| 打开已关联的目录、资料和网页链接 | 纳管执行程序、自动调度 |
| 本地备份、恢复、基本导出 | 手机同步、Outlook 联动 |

**第一版不是只有资料列表。**它必须形成：

**快速记录 → 登记项目 → 检索找回 → 安排下一步 → 留下工作记录 → 重启软件后继续工作。**

运行能力紧接着进入 **P2**，三种执行模式进入 **P3**。不能因为做日历、换主题或接 AI，把运行能力无限后移。

## 1.3 最重要的取舍

**先管理，不先自动化；先可靠手动执行，不先写完整调度引擎；先恢复上下文，不先做复杂项目报表。**

另外有三条贯穿所有阶段：

- **登记不等于信任，发现代码不等于允许执行。**
- **任务到了计划日期，不等于获得程序执行授权。**
- **程序退出码为零，不等于项目成果已经验证可用。**

# 2. 需求与优先级

## 2.1 核心问题与具体能力的对应关系

| 核心问题 | 对应能力 | 优先级与实际效果 |
|---|---|---|
| A：忘记做过什么，不知道能否复用 | 用途描述、功能关键词、开放标签、普通检索、可用程度、验证时间、来源入口 | **P1 必须实现。**先找到，再根据证据判断复用，不用 AI 评分替代事实 |
| B：做到一半，回来不知道接着干什么 | 工作记录、阻塞点、唯一的当前下一步、相关文件或对话、计划继续日期 | **P1 的核心。**项目详情首先显示恢复工作所需内容，而不是统计图 |
| C：想法没有及时记录和安排 | 一句话收集、收件箱、复查日期、转项目或任务、保留原文 | **P1 必须实现。**记录时不要求分类或填写项目表单 |
| D：成果需要反复使用，但不想全部常驻 | 多运行入口、原环境复用、运行历史、三种模式、暂停与跳过 | **P2 手动运行，P3 三种模式。**只运行选中的入口，不把所有项目变成后台任务 |
| E：管理工具本身不能成为负担 | 极少必填字段、渐进补全、统一任务数据、无自动上传、适度提醒 | **所有阶段的限制条件。**新增功能必须减少实际操作，而不是增加维护义务 |

## 2.2 已确认、建议与暂定假设

**已经确认的需求**：Windows 优先；本地数据目录由你选择；项目类型开放；既有手工登记也有审核式自动发现；多数项目在本地，部分在 GitHub；手机应用和工作服务程序当前仅登记；在线 AI、上传、同步均不能默认启用。

**本方案提出的建议**：

一开始只维护一个桌面版本；项目登记只强制填写名称；“下一步行动”引用一条任务，而不是另存一份容易失步的文本；先支持非交互式短时程序；所有自动执行都必须建立在已经审查并验证过的运行配置上。

**暂定假设，不代替授权**：

| 假设 | 当前采用的保守处理 |
|---|---|
| 目标电脑的具体 Windows 版本、架构未知 | 首先验证仍受支持的 Windows 11 x64；其他环境另行验证，不笼统承诺兼容 |
| 管理数据放在哪种磁盘上未知 | 首版支持本机固定磁盘；不把网络共享或云同步文件夹作为活动数据库位置 |
| 是否需要多个工作区未知 | 首版一个工作区、单用户、单实例；可切换数据目录，但不并行调度多个工作区 |
| 同时运行多少程序未知 | P2、P3 默认全局一次运行一个程序，同一入口不得并发 |
| 多久算“长期未推进”未知 | 建议从 14 天开始，仅作用于明确处于进行中的项目，可调整或关闭 |
| 对话导出格式未知 | 第一版只关联原文件或链接；不假定格式一致 |
| 是否备份到 GitHub 未确定 | 不上传，不自动提交，不自动创建远程仓库 |

测试中的“50、500、2,000 个项目”只是验证规模，不是对你实际项目数量的判断。

## 2.3 后置与明确不做

**后续可选**：完整日历、里程碑和简单依赖、Windows 通知、半自动入库、对话解析、有限 AI 辅助、简易本地服务管理、手机只读查看、Outlook 只读联动。

**明确不做**：企业权限体系、团队协作平台、云端执行服务器、远程工作服务执行、手机应用部署、自动安装项目依赖、自动修改原项目、通用插件市场、通用工作流引擎、常驻大模型、独立向量数据库。

这些不是“技术上做不到”，而是对当前个人使用价值不够高，同时会扩大维护成本或安全边界。

# 3. 关键用户流程

## 3.1 记录想法：先收下，再整理

在任意主要页面点击“快速记录”，输入一句话，例如“做一个比较几个报告差异的工具”，直接保存。

系统建立想法记录，保留原文和创建时间，不要求名称、类型、优先级、截止日期。之后在想法收件箱中，可以补充来源、设置复查日期、搁置，或者转成项目或任务。

转换后保留原始想法和转换关系，不删除来源；重复点击转换时打开已生成的目标，不重复创建。

## 3.2 登记已有项目：不要求先证明它完整

点击“新建项目”，填写名称即可保存。建议顺手填写一句用途，但不设为硬性门槛。

随后按需要添加目录、GitHub 地址、对话文件、说明文档。一个项目可以关联多个目录，也可以一个目录都没有。类型与标签允许自定义。

保存后显示的是：

> “已登记；关联一个本地目录；成果尚未验证；没有运行配置。”

不能因为目录中有 Python 文件，就自动显示“可运行”。

## 3.3 查找可复用项目：先找到，再比较证据

输入“采集”“网页 截图”或“报告 对比”，结合类型、开发状态、成果可用程度筛选。

结果卡片显示：解决的问题、命中的描述、成果可用程度、最后验证时间、来源是否有效。进入详情后，查看最近工作记录、运行说明和已知限制。

复用判断优先依据：

**功能是否接近 → 成果是否验证 → 当前环境是否可用 → 改造成本是否已有说明。**

不生成没有依据的“复用价值 92 分”。

## 3.4 继续昨天未完成的工作：恢复卡片优先

打开今日工作台，选择昨天安排继续的任务。进入项目后，最上方显示：

> 上次完成：已能抓取第一页数据。  
> 当前阻塞：第二页请求参数还没有确认。  
> 下一步：检查请求日志，确定第二页参数。  
> 应打开：项目目录、相关日志、指定对话。  
> 计划继续：今天。

点击对应入口打开资料。结束工作时，用“记录本次进展”更新已完成事项、阻塞点和下一步。

不要求写正式日报；可以只写一句进展和一个具体下一步。

## 3.5 手动执行程序：P2

在项目详情新增一个运行入口，例如“生成报告”。

选择现有解释器或可执行文件，设置参数、工作目录和输出位置；Python 项目优先直接选择它自己的虚拟环境解释器，不执行环境激活脚本，也不自动安装依赖。

首次运行前，展示实际程序、参数、工作目录、可能的输入输出和权限提醒。确认后执行，显示日志与状态。结束后保留退出码、开始结束时间、输出位置。

只有你核查成果后，才把“成果已验证可用”写入项目档案。

## 3.6 配置提醒或自动执行：P3

先选择已经配置好的运行入口，再选择执行模式。

“提醒后执行”需要设置时间规则，到期只产生待确认事项；确认当前这一次执行后才启动。

“自动执行”需要额外审查：程序与参数、规则、有效期、错过执行策略、是否可能产生外部副作用。界面展示接下来几次预计触发时间，明确确认后才启用。

由“提醒后执行”切换成“自动执行”时，不把以前积压的待确认事项自动放行。

## 3.7 审核自动发现候选：P5

选择明确的目录或文件，查看扫描范围、排除项和读取上限，再启动只读扫描。

每个候选展示：识别原因、来源文件、原文片段、推测字段、不确定项、疑似重复对象。

你可以修改、拆分为多个项目、关联已有项目、拒绝，或确认新建。正式入库前，候选与正式项目严格分开。

下次扫描只能提出新的候选或修改建议，不能直接改写你已经确认的项目字段。

# 4. 页面与交互结构

## 4.1 导航按阶段出现，不预先摆满空页面

| 页面 | 主要内容和动作 | 出现阶段 |
|---|---|---|
| 今日工作台 | 今天准备做、近期计划、待复查、需补上下文的进行中项目 | P1 |
| 项目库 | 检索、筛选、登记、收藏常用成果 | P1 |
| 项目详情 | 恢复上下文、任务、来源、成果状态；以后增加运行入口 | P1 |
| 想法收件箱 | 一句话记录、复查、转换、搁置 | P1 |
| 设置与数据 | 数据位置、备份恢复、导出、隐私设置 | P1 |
| 执行中心 | 运行入口、当前运行、历史、规则 | P2、P3 |
| 任务与日历 | 同一份任务的列表、看板、日历视图 | P4 |
| 导入审核 | 候选、依据、重复提示、字段差异 | P5 |

第一版可以把任务列表放在今日工作台和项目详情里，不必立即增加独立的任务模块。

## 4.2 最常用操作如何减少负担

项目表单只常显“名称、用途、来源”三个区域，其余信息按需展开。默认状态不要求你反复选择。

“下一步”可以直接在项目详情中编辑，底层创建或更新对应任务，而不是要求先跳转到任务管理页面。

快捷操作只先做应用内快捷键：快速记录、搜索、保存。全局快捷键与托盘入口后置，避免一开始处理系统冲突。

对资料操作区分“查看文本”“打开所在目录”“用外部应用打开”。脚本文件不能借“打开文档”的动作被直接执行。

## 4.3 首页不机械制造焦虑

“长期未推进”只考虑进行中的项目，并使用真实工作记录、明确完成任务等活动判断。

修改标签、扫描目录、查看详情、文件修改时间、例行运行采集程序，都不自动算作开发进展。

暂停、归档、等待外部条件、已完成且作为工具使用的项目，不进入普通的停滞催促。等待中的项目只在你设置的复查日期出现。

昨天没完成的计划不无限自动滚入今天，而是进入“待重新安排”。

## 4.4 列表、看板、日历只有一个数据源

三者都是任务的不同视图：

**列表修改状态、看板拖动状态、日历调整计划时间，最终都修改同一条任务。**

日历拖动只改变计划时间，不顺带修改截止日期，更不能改变程序执行规则。以后日历展示执行计划时，应使用单独样式，并通过明确的规则编辑入口修改。

# 5. 数据模型与状态设计

## 5.1 最少必填与逐步补充

**项目唯一必填：名称。**系统生成稳定 ID、创建时间和默认状态。

建议补充一句“解决什么问题”。类型、标签、目录、仓库、对话、运行环境、下一步、计划日期都可以以后补全。

**想法唯一必填：原始内容。**

**任务唯一必填：任务名称。**项目关联、计划日期、截止日期、预计投入都可以为空。

## 5.2 核心实体

下面是目标模型，不要求第一轮把全部表建出来。

| 实体 | 必要字段与关系 |
|---|---|
| **项目 Project** | ID、名称、用途、功能说明、开放类型与标签、开发状态、成果可用程度、归档标记、当前下一步任务 ID、验证时间与说明 |
| **想法 Idea** | 原文、状态、来源、复查日期、转换目标关系 |
| **任务 Task** | 名称、可选项目 ID、任务状态、优先级、计划日期、可选截止日期或时刻、预计投入；P4 增加子任务、里程碑和依赖 |
| **工作记录 WorkLog** | 项目、记录时间、本次完成、当前阻塞、当时的下一步快照、相关来源；历史记录不随当前任务改名而被重写 |
| **来源资料 Source** | 类型、外部路径或 URL、引用/副本方式、原始提供方、可选定位信息、检查状态、可选内容指纹 |
| **关联关系** | 项目与来源多对多；一份对话可关联多个项目，一个项目可关联多个目录或对话 |
| **运行配置 RunConfig** | 所属项目、名称、执行类型、程序绝对路径、参数数组、工作目录、环境设置、凭据引用、输入输出声明、超时、模式、配置版本 |
| **执行授权 Approval** | 对应配置及规则版本、关键内容指纹、授权时间、授权范围、撤销原因；不能由导入文件自行声明有效 |
| **调度规则 ScheduleRule** | 运行配置、规则类型、时间及时区、有效期、状态、错过执行策略、版本 |
| **触发实例 Occurrence** | 某条规则在某个计划时刻的一次触发；记录待确认、跳过、过期、已消费等状态 |
| **运行记录 Run** | 运行配置快照、触发来源、可选触发实例 ID、状态、时间、退出码、进程标识、日志和输出位置、失败原因 |
| **通知 Notification** | 对应任务、想法或触发实例，提醒时间、已读、延后、忽略状态；不保存程序执行权限 |
| **导入批次与候选** | 扫描范围、候选身份、提取字段、依据位置、解析器版本、不确定性、审核决定、目标项目 |

“当前下一步”以 `Project.next_task_id` 指向的任务为准。工作记录里的下一步只是一份历史快照，不构成第二个可编辑的当前值。

“最近运行结果”从运行记录计算，不能随手维护一个独立的“最近成功”字段，否则容易与历史失步。

## 5.3 三套状态必须分开

| 状态维度 | 建议取值 | 说明 |
|---|---|---|
| 项目开发状态 | 待开展、进行中、等待、暂停、已完成 | 表示开发和推进情况；归档另外记录 |
| 成果可用程度 | 未验证、原型、可用、需要修复 | 表示成果现在是否可用，必须允许“已完成但已失效” |
| 任务状态 | 待办、进行中、阻塞、完成、取消 | 不因计划日期过去而自动完成或取消 |
| 程序运行状态 | 排队、启动中、运行中、取消中、成功、失败、取消、结果未知 | 表示一次执行的观察结果 |

例如，一个采集工具完全可以同时是：

> 开发状态：已完成；成果：可用；最近运行：失败，原因是网络超时。

这不意味着它重新变成“开发中”，也不意味着它永远不可用。

## 5.4 能力标签不是承诺

建议把能力设计为可组合的标记，而不是单一状态：

**已登记**：有档案即可。  
**有可打开来源**：存在目录、文档或链接，但远端链接可以标注“未验证可达”。  
**已配置本机运行**：存在运行配置。  
**已验证可运行**：配置经过明确测试，而且关键入口没有发生变化。

“仅记录”项目禁止出现误导性的运行按钮。手机应用、工作服务项目当前保持这个策略，扫描不得擅自改变它。

路径检查通过只能说明路径存在，不能等同于依赖完整、业务逻辑正确。

## 5.5 日期、里程碑与依赖

计划日期表示“打算什么时候做”，截止日期表示“最晚什么时候完成”。两者都可以为空，延期计划不自动延长截止日期。

纯日期按日期保存，不强行转换成午夜 UTC。真实触发时刻保存 UTC，同时保留规则时区。

P4 的依赖只先支持同项目内的“前项完成后再开始后项”，禁止循环；不自动计算关键路径，不自动启动程序。里程碑可以实现为特殊任务及关联任务集合，不另建复杂计划引擎。

# 6. 架构与技术决策

## 6.1 候选路线比较

下表中的资源与开发难度属于**针对本项目的工程判断，尚未实测**，不是框架性能排名。

| 维度 | C#/.NET + WPF | Tauri + Web 前端 | Python + PySide6 | Electron |
|---|---|---|---|---|
| Windows 适配 | 与本项目目标最直接，适合文件、进程、窗口操作 | 可满足，但需要 Rust 与 Windows API 衔接 | 可满足，特殊 Windows 能力仍需适配 | 可满足，复杂进程树控制仍需本机适配 |
| 应用运行资源 | 不需要浏览器引擎；适合作为低空闲负担的基线 | 需要统计核心进程与 WebView 进程，不能只看主进程 | 取决于 Qt 模块、解释器和打包方式 | 自带 Chromium、Node.js，基础组件较多 |
| 冷启动 | 值得优先验证；不能保证天然最快 | 受 WebView 初始化影响，需要实测 | 打包模式可能明显影响启动，需实测 | 对简单管理器而言，启动组件偏多，需实测 |
| 安装体积 | 自包含发布会带运行时；换来目标机部署简单 | 需明确目标机 WebView2 是否已有、怎样离线部署 | 需处理 Python、Qt、插件等打包内容 | 需要携带浏览器与 Node.js |
| 进程与权限 | 可用 .NET 和 Win32，平台适配集中 | Rust 核心控制，前端不能拥有任意执行权 | QProcess 可负责基础启动，完整进程树仍需专项验证 | 主进程负责执行，渲染界面必须隔离 |
| 托盘与通知 | 托盘可用 Windows Forms 组件；系统通知后接 Windows App SDK | 有相应能力，但仍需权限和打包验证 | 托盘可做，Windows 通知另行集成验证 | 有桌面能力，但仍需处理平台与安全配置 |
| AI 开发与调试 | 主体一套语言和类型系统；XAML 绑定需要检查 | TypeScript、Rust、IPC 三个层面，定位链更长 | 原型较快，但环境、线程和分发问题不能省略 | Web 界面开发便利，但进程边界和依赖维护更多 |
| 更新维护 | 自包含版本需要随应用更新运行时；可先手动更新 | 需兼顾核心、前端、插件和 WebView 策略 | 需固定 Python、Qt、打包工具组合 | 需持续维护 Electron 及其运行时依赖 |
| 后续扩展 | 当前 Windows 功能成本较低；手机界面将来另做 | 更利于复用部分 Web 界面，但不自动获得同步能力 | 适合已有大量 Python 桌面组件时考虑 | 有 Web 组件生态优势，但当前收益不足以抵消复杂度 |

官方资料确认：Tauri 使用核心进程与 WebView 的多进程模型，并提供权限能力机制；Windows 分发还涉及 WebView2 部署策略。PySide6 有官方部署工具，但它本身也是编译与打包链路，而不是“Python 脚本直接变成一个没有依赖的小文件”。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)

Electron 官方明确其包含 Chromium 和 Node.js，并只支持最近三个稳定大版本；对这个以本地资料、任务和进程控制为主的工具，这意味着额外的更新维护范围，因此不作为主选。[Electron 官方说明](https://www.electronjs.org/docs/latest/why-electron)

### 主方案的具体组成

**界面**：WPF，采用简单 MVVM；可使用 `CommunityToolkit.Mvvm` 减少重复绑定代码，不引入大型桌面框架。该工具包是官方 .NET Community Toolkit 的组成部分。[MVVM Toolkit](https://learn.microsoft.com/en-us/dotnet/communitytoolkit/mvvm/)

**存储**：SQLite，通过 `Microsoft.Data.Sqlite` 访问，参数化查询、明确事务、少量版本化迁移；第一版不引入 ORM。官方说明这个库可以独立使用，不依赖 Entity Framework。[Microsoft.Data.Sqlite](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/)

**执行**：一个 Windows 平台适配模块，负责参数编码、进程树、取消、超时和日志。

**调度**：应用进程内的轻量调度器，不安装 Windows 服务，不创建大量系统计划任务。

### 备选方案的切换条件

只有同时满足下面的判断，才讨论 Tauri：

主方案在真实 Windows 原型中暴露出重要且持续的界面或维护障碍；Tauri 原型在相同打包、启动、内存、进程控制测试中通过；你愿意承担 Rust 与 TypeScript 两套代码的维护。

**“AI 觉得 Web 页面更好写”不是足够的切换理由。**

## 6.2 模块边界与数据流

生产代码先控制在三个主要工程：桌面界面、业务核心、本地基础设施，再加测试工程。无需按每个功能拆成独立服务。

| 模块 | 负责什么 | 不允许做什么 |
|---|---|---|
| 界面与 ViewModel | 展示、输入、发起用户动作 | 直接拼命令、直接修改调度状态表 |
| 项目与计划服务 | 项目、想法、任务、上下文、查询 | 执行导入资料中的指令 |
| 存储与数据服务 | 事务、迁移、备份、导出 | 维护另一套与数据库冲突的项目 JSON |
| 导入器 | 只读提取、输出候选和依据 | 写原项目、安装依赖、运行命令 |
| 调度器 | 计算触发、生成实例、去重、检查有效期 | 绕过授权直接启动进程 |
| 执行器 | 最后校验、启动、观察、停止、记录结果 | 自动获取管理员权限、自动重跑未知结果 |

主要数据流：

**资料 → 导入候选 → 人工审核 → 正式数据。**

**用户点击或到期触发 → 授权与配置校验 → 排队 → 执行器 → 运行记录。**

所有入口最终经过同一执行器，不能给“自动模式”另写一条绕过校验的捷径。

## 6.3 SQLite 是否合适

合适。本项目属于单用户、嵌入式、本地文件型桌面应用，正是 SQLite 官方列举的适用场景之一。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

建议第一版使用默认回滚日志模式、短事务、串行写入，并显式启用外键约束。暂不为了“高并发”加入 WAL；后续只有实际出现读写竞争时再评估。

即使以后采用 WAL，也不能把活动数据库放到网络文件系统，更不能只复制主数据库文件就认为备份完整。SQLite 官方明确了 WAL 的同机限制及附加日志文件行为。[SQLite WAL](https://sqlite.org/wal.html)

数据库工作不能阻塞界面线程。尤其不能以为调用了名字带 `Async` 的方法就自动变成后台 I/O；`Microsoft.Data.Sqlite` 官方说明其异步 ADO.NET 方法实际仍同步执行。因此查询、导入和备份应通过受控后台工作执行。[异步限制](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async)

## 6.4 中文检索：第一版采用可验证的朴素方案

**不默认上向量检索，也不直接把默认 FTS5 当成中文搜索已经解决。**

P1 的方案是：

统一生成可重建的检索文本，覆盖名称、用途、功能说明、类型、标签和人工别名；进行 Unicode 规范化、英文大小写统一和空白处理。查询以参数化的字面子串匹配为基础，支持空格分开的多个关键词，默认要求各关键词都出现。

例如：

| 输入 | 预期行为 |
|---|---|
| `采集` | 可以命中“网页数据采集”“定期采集报价” |
| `网页 截图` | 两个词可以分别出现在名称、用途或标签中 |
| `Excel` | 与 `excel` 一致 |
| `%`、`_` | 按普通字符处理，不意外变成通配符 |
| `抓取` | 只有正文或人工别名包含该词时命中，不假装已经理解所有近义词 |

排序使用明确规则：名称和标签匹配优先，其次用途和功能说明；展示命中片段。成果可用程度和验证时间用于判断复用，不掩盖文本相关性。

这能保证普通中文短词查找，但**不是自然语言问答**。输入一整句没有共同字面的描述，可能找不到；界面应提示拆成关键词，而不是声称语义理解。

数据规模扩大且实测检索不达标后，再评估 FTS5 trigram。官方文档明确指出，trigram 全文查询不能匹配少于三个 Unicode 字符的子串，因此“采集”“报告”这类两字查询仍必须有回退方案。[SQLite FTS5](https://sqlite.org/fts5.html)

## 6.5 数据目录与唯一数据源

建议结构：

```text
用户选择的数据目录/
  workbench.db       项目、任务、设置、运行配置等权威数据
  attachments/       用户明确导入的资料副本
  logs/              受控运行日志和应用诊断日志
  secrets/           本机加密凭据，普通导出与默认备份不包含
  backups/           已完成并验证的备份
  cache/             可重建索引和预览缓存
  staging/           未完成导入、备份的临时文件
```

被管理源码、外部对话原文件、业务程序输出目录仍在原位置，不要求迁入上述目录。

数据库是管理元数据的唯一权威来源；附件文件是导入内容的权威副本，数据库仅保存描述和定位；缓存可以删除重建。普通设置不再另外保存一份项目配置 JSON。

程序安装目录之外，可以有一个很小的启动定位文件，用于记住数据目录位置，但它不保存项目内容。原数据目录不可访问时，应提示修复或选择目录，不能偷偷新建空数据库，让你误以为数据丢了。

## 6.6 一致性备份、恢复和迁移

**备份不是直接复制正在使用的数据库文件。**采用 SQLite Backup API；Microsoft.Data.Sqlite 也提供对应备份能力。[SQLite Backup API](https://sqlite.org/backup.html)

建议流程：

**第一步：进入备份窗口。**暂停接纳新的运行任务，等待当前运行结束；冻结管理数据写入和附件增删，不强行终止业务程序。

**第二步：生成一致快照。**数据库通过 Backup API 写入临时备份目录；按快照中的附件清单复制已提交、不可变的附件。外部源码和引用资料只记录引用，不偷偷纳入备份。

**第三步：校验。**检查数据库完整性、外键、附件是否齐全、文件校验值，并生成包含应用版本、数据库版本、时间和内容清单的清单文件。

**第四步：提交备份。**全部成功后，才把临时备份标记为完成。失败的备份不能混在“可恢复备份”列表中。

**第五步：恢复演练。**恢复到另一个空目录，核对项目、任务、来源和附件，再切换工作区。恢复失败不能覆盖原数据。

恢复后有三个特殊处理：

- 外部路径可能失效，提供“旧根目录 → 新根目录”的预览式重映射，只改引用，不移动源码。
- 本机凭据可能无法恢复，显示“凭据缺失”，要求重新输入。
- **所有自动执行授权失效，规则暂停。**恢复旧备份不能导致历史任务重新执行。

P1 提供手动备份、迁移前自动备份，以及应用运行期间、数据发生变化后的低频本地备份。建议保留最近若干份及升级前备份，数量可设置。同一磁盘上的备份主要防误操作，不应描述成磁盘损坏后的完整保障。

导出先提供带格式版本的 JSON，供迁移和长期可读保存；它不是实时第二数据源。普通导出不含凭据、有效执行授权、原始日志和未经选择的附件。

升级采用版本化迁移：先备份、再迁移、校验后启用。旧程序遇到更高版本数据库，应拒绝写入，不能尝试“自动降级”。

## 6.7 隐私与执行安全边界

**管理器默认无后台上传、遥测、在线摘要或仓库拉取。**用户点击仓库链接打开浏览器，与软件后台传输资料是两件事。

密钥采用 Windows DPAPI 的当前用户范围保护，数据库保存凭据引用，不保存明文。DPAPI 依赖用户或计算机凭据，因此不能把复制加密文件视为可靠的跨电脑迁移方案；换电脑或账户时按重新输入凭据设计。[Windows 数据保护](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection)

普通环境变量与秘密变量分开。秘密不放在命令行参数中，不写入工具自己的日志；对配置过的秘密进行输出脱敏。敏感入口默认不保存标准输出和标准错误，只保留状态元数据。任意外部程序可能输出未知或变形后的秘密，不能承诺一个通用脱敏器可以完全识别。

导入资料按不可信数据处理：不执行 Markdown 中的命令，不渲染可执行 HTML，不自动加载远程图片，不通过扫描调用解释器、包管理器、Git 钩子或配置脚本。

运行接口对外接收“程序路径＋参数数组”，不接收默认交给 Shell 的整段字符串。.NET 的 `ArgumentList` 提供参数集合和转义机制；需要 Win32 原生启动时，也必须集中在一个经过测试的参数编码适配器中，不能到处拼接命令行。[ProcessStartInfo.ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist?view=net-10.0)

P2、P3 不支持任意 Shell 片段、管道、重定向、命令替换。`.bat`、`.cmd`、PowerShell 脚本先保留为说明资料；以后确有需要，再作为显式高风险入口单独审查，而不是悄悄包一层 Shell。

程序以当前普通用户权限运行，不默认提权。输入输出目录声明用于审查和定位，**不是对脚本读写能力的隔离**。被授权程序仍可能访问当前用户有权访问的文件和网络资源。

**可执行路径限制、入口哈希、Job Object 都不是完整沙箱。**

## 6.8 打包与本地 HTTP 的边界

P0 就产出 **Windows x64 自包含发布目录**，压缩后解压，双击 EXE 启动。先不追求“只有一个 EXE”。自包含发布包含应用所需的 .NET 运行时，目标机不必预先安装该运行时；代价是包体更大，后续运行时修补需要随应用重新发布。[.NET 部署](https://learn.microsoft.com/en-us/dotnet/core/deploying/)

正式数据必须与程序目录分离。第一版手动替换程序版本；安装器、代码签名和自动更新后置。以后安装器只能管理程序文件和快捷方式，卸载默认保留数据与全部外部源码。

主方案不开放本地 HTTP 端口。即使切换 Tauri，也优先使用它的桌面 IPC，而不是额外启动 HTTP 服务。

若未来确有必须使用本地 HTTP 的功能，最低要求是只监听回环地址、使用会话级身份校验、校验 Host 与 Origin、防止跨站请求、禁止通配 CORS、禁止 GET 执行副作用。**随机端口和“只监听 localhost”都不能单独作为执行接口的安全措施。**

# 7. 执行、日程与异常处理

## 7.1 三种模式的行为表

执行模式属于**运行配置**，不是整个项目。一个项目的“采集数据”和“生成报告”可以使用不同模式。

| 模式 | 到期后的行为 | 需要的授权 | 未确认或应用离线时 |
|---|---|---|---|
| 手动执行 | 不因日期到期而执行 | 本次明确点击；首次或配置变化时审查 | 不运行 |
| 提醒后执行 | 创建待确认事项 | 对当前触发实例明确确认 | 保持待确认或过期，绝不自动转运行 |
| 自动执行 | 校验规则、授权、环境后执行 | 事先明确授权该配置版本及规则 | 按错过策略处理，默认跳过 |
| 提前提醒＋倒计时自动执行 | 仍属于预授权自动执行，而不是普通提醒 | 单独授权并允许取消 | 后续可选，不进入 P3 |

普通手动运行按钮在配置有效时仍可使用，但不能绕过已有的运行占用、配置变更或凭据检查。

## 7.2 首个调度版本只支持必要子集

P3 支持：

**一次性指定日期时刻；每周选定星期与时刻；可选生效开始和结束时间。**

每天执行可以表示为选中全部星期。不引入 Cron 表达式、节假日规则、复杂月历或无限组合。

“每隔若干分钟执行”后置：它需要额外明确从上次计划时间还是完成时间起算，容易造成连续占用。确有高价值场景时，优先加入“完成后间隔”的固定延迟模式。

规则保存时展示时区、有效期和未来几次触发时间。时间不存在的夏令时日期跳过；重复的本地时刻只触发一次，不因系统时钟回拨产生重复运行。

## 7.3 三层状态机

**规则：**草稿 → 已启用 ↔ 已暂停 → 已关闭；到期进入已过期，关键配置变化进入待重新授权。

**触发实例：**已到期 → 待确认或已排队 → 已消费；也可以进入跳过、过期、取消。

**一次运行：**排队 → 启动中 → 运行中 → 成功／失败／取消／结果未知；取消过程必须有“取消中”，不能按下按钮就假定已经停止。

触发实例与运行记录分开，才能表达“提醒产生过，但用户没有执行”，而不伪造一条失败运行。

## 7.4 必须固定的异常规则

| 情况 | 默认处理 |
|---|---|
| 重复点击运行 | 后端按运行入口和请求身份去重；打开现有排队或运行项，不依赖按钮防抖 |
| 同一入口尚未结束又到期 | 本次标记“因仍在运行而跳过”，不无限积压 |
| 其他入口占用全局运行位 | 有限排队；每个入口最多保留一个未开始请求，超过启动窗口则过期 |
| 睡眠、退出、重启期间错过多次 | 默认全部跳过并汇总显示；可选“恢复后询问一次”，不能批量补跑 |
| 从睡眠恢复 | 重新计算未来触发；过去时刻走错过策略，不直接补执行 |
| 应用崩溃，原记录停在启动中或运行中 | 标记结果未知，暂停相关自动规则，要求核查输出；不误报成功，不盲目重跑 |
| 暂停一条规则 | 取消其尚未开始的待确认和排队项；已运行项继续，另提供停止操作 |
| 切换模式 | 作废旧模式未开始的调度请求，从新的未来触发开始；旧待确认不能变成自动任务 |
| 修改运行配置 | 取消该入口未开始的请求，撤销旧授权；已运行任务保留原快照 |
| 跳过本次 | 只取消当前或指定的一个触发实例，不关闭未来规则 |
| 取消运行 | 先尝试受支持的正常退出，再按确认的策略终止受管进程树；停止未确认前不显示已取消 |
| 超时 | 停止进程；确认停止后记失败并注明超时，无法确认则结果未知 |
| 执行失败 | 默认不自动重试；人工重试创建新的关联记录 |
| 缺路径、缺凭据、入口变化 | 阻止启动并暂停自动规则，不反复定时失败 |
| 连续业务运行失败 | 建议达到可配置阈值后暂停规则，只发一次汇总提醒 |
| 归档项目 | 明确提示并默认暂停其规则；已运行任务另外处理 |

应用恢复后的补跑，即便未来加入，也只能是**明确授权的合并补跑一次**，不能把错过的几十次实例逐条补跑。

## 7.5 授权绑定什么内容

授权至少绑定：

可执行程序及入口文件、参数、工作目录、环境设置和凭据引用版本、关键输入输出配置、执行模式、时间规则、有效期及错过策略。

关键入口内容变化后，自动授权失效。再次运行前展示差异，重新审查。

但只检查入口文件不能证明所有被导入模块、依赖或远端行为都没有变化。这个机制用于发现常见配置漂移，**不构成恶意代码完整性验证**。

新导入、复制、恢复出来的运行配置默认没有有效自动授权。

## 7.6 进程树、崩溃与“恰好一次”的限制

建议使用 Windows Job Object 管理受管进程树，配置相应的关闭终止行为。官方机制允许统一管理关联进程，并可在最后一个作业句柄关闭时终止其中的进程。[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

关键要求是启动时就建立约束，不能让目标先自由运行，再补挂进程组。P0 要验证创建时加入作业的方案，或经过验证的挂起创建、加入作业、再恢复方案，并覆盖失败清理。微软官方资料也指出，先启动再加入作业存在时间窗口问题。[创建进程时加入 Job Object](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812)

数据库先持久化启动意图，再启动程序；触发实例使用唯一键，执行器启动前再次检查规则和授权版本。

这可以减少重复启动，但**不能承诺任意外部程序的业务副作用“恰好发生一次”**。程序可能已写出文件，管理器却在记录结果前崩溃。此时正确答案是“结果未知，人工核查”，不是自动重跑。

## 7.7 日志与结果

每次运行保存配置的脱敏快照、触发来源、开始结束时间、退出码、终止原因、日志位置和输出位置。

标准输出与错误输出需要同时持续读取；日志有大小和总保留量上限，界面只展示有限尾部内容，不能把整个日志长期保留在内存中。达到上限仍要继续排空输出，不能因为停止读取导致子进程卡住。

“成功”默认只表示观察到正常退出且满足配置的退出码条件。输出文件缺失、日志不完整、业务结果未验证，都要另外显示。

## 7.8 应用生命周期约定

| 应用或电脑状态 | 调度与提醒 | 受管程序 |
|---|---|---|
| 主窗口打开 | 可用 | 可运行 |
| 最小化到任务栏 | 可用 | 继续 |
| 用户已选择托盘常驻，关闭主窗口 | 可用；有托盘状态指示 | 继续 |
| 未启用托盘常驻，关闭窗口 | 按完全退出处理；存在运行任务时先提示 | 等待结束或明确停止后退出 |
| 完全退出 | 不再调度，不产生新的到期提醒 | P2、P3 不支持脱离管理器继续运行 |
| 系统睡眠、休眠 | 不保证执行或提醒，不主动唤醒电脑 | 不承诺持续工作；恢复后核对状态与超时 |
| 应用再次启动 | 恢复管理数据，汇总错过事项，计算未来触发 | 不自动重跑未确认结果 |

开机启动与关闭到托盘分别设置，默认关闭。托盘可使用 Windows Forms `NotifyIcon`，不需要为了托盘先引入整套 Web 或后台服务架构。[NotifyIcon](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/controls/notifyicon-component-overview-windows-forms)

## 7.9 短时任务与本地服务

P2、P3 只纳管**执行后退出的非交互式程序**。等待终端输入的程序、需要提权的程序、借外部系统服务启动独立进程的程序不在首个执行版本支持范围内。

本地 Web 服务作为后续小扩展，仅支持：

人工启动 → 检查声明的本机端口或就绪条件 → 用户打开页面 → 人工停止。

不做自动重启、反向代理、部署编排、复杂健康检查。端口被占用时报告冲突，不能自动杀掉占用端口的未知进程。

被管理项目自身提供 Web 服务，不等于工作台需要开放本机执行 API。

# 8. 分阶段实施计划

每个阶段完成后都应产生可双击启动的版本、测试结果和明确的未完成清单。P0 是技术验证版本，P1 才是投入日常使用的 MVP。

> 阶段衔接：以下保留第一轮路线。当前第一阶段以第二轮六批方案为准；不把执行器实验当作当前管理 MVP 的功能，也不以 P0 原型结束第一阶段。

## P0：先验证桌面交付与关键技术风险

**目标：**确认选型能在目标 Windows 上真实运行，而不是只在开发环境里展示页面。

**小批次：**  
P0-A：最小 WPF 窗口、自包含打包、普通用户双击启动。  
P0-B：选择数据目录、SQLite 写入重启读取、单实例、中文和空格路径。  
P0-C：中文检索试验、数据库备份恢复试验。  
P0-D：只使用测试程序验证参数、输出、超时、子进程与崩溃清理。

**交付物：**技术验证包、环境记录、性能基线、关键决策记录。

**验收：**没有开发环境的目标 Windows 可以启动；数据重启后存在；备份可恢复；测试进程可以可靠观察和清理。

**主要风险与边界：**原生进程管理是重点风险。失败时缩小范围并修复，不开发调度页面掩盖问题；不接入真实个人脚本，不做正式业务界面。

## P1：管理 MVP

**目标：**完成记录、找回、安排下一步、恢复上下文的闭环。

**小批次：**  
P1-A：项目、想法、来源的最小数据及增改查。  
P1-B：中文检索与筛选。  
P1-C：任务、下一步、工作记录。  
P1-D：今日工作台与安全打开来源。  
P1-E：备份恢复、版本化导出、首次使用与错误提示。

**依赖：**P0 的打包、数据和检索验证通过。

**交付物：**可日常使用的桌面版本、示例数据、完整恢复流程。

**验收：**登记代表性项目后，第二天可以找回并理解下一步；只有对话或想法的项目也能保存；恢复备份后内容完整。

**主要风险与边界：**表单过重、下一步出现多份不一致数据。禁止增加运行引擎、扫描、复杂日历和 AI 接口。

## P2：安全手动运行

**目标：**让已有成果真正可以按需使用。

**小批次：**  
P2-A：运行配置、路径和环境预检查、授权展示。  
P2-B：执行器、参数测试、进程树、取消与超时。  
P2-C：运行记录、有限日志、输出定位、凭据处理。  
P2-D：重复点击、异常退出、重启未知状态与退出交互。

**依赖：**P1 稳定，P0 的进程试验通过。

**交付物：**手动执行中心及测试程序集合。

**验收：**能够用已有 Python 环境运行代表性短时任务；不安装依赖；异常、取消、重复点击和崩溃恢复都可解释。

**主要风险与边界：**参数转义、日志阻塞、子进程残留。禁止加入自动调度、任意 Shell、后台服务托管。

## P3：三种模式与有限调度

**目标：**完成手动、提醒确认、明确授权自动执行。

**小批次：**  
P3-A：规则、触发实例、可替换测试时钟。  
P3-B：应用内提醒、确认、延后、忽略。  
P3-C：授权校验、去重、错过策略、暂停和模式切换。  
P3-D：托盘生命周期、睡眠恢复、时间变化与崩溃测试。

**依赖：**P2 的执行器通过异常测试。

**交付物：**有限规则调度器、执行规则页面、应用内提醒中心。

**验收：**未确认的提醒零执行；恢复后不批量补跑；暂停和配置变化不会放行旧队列；完全退出后明确不调度。

**主要风险与边界：**重复触发、旧授权生效、通知与授权混淆。禁止加入 Cron、复杂间隔、自动重试和倒计时自动执行。

## P4：更完整的推进与通知

**目标：**改善安排体验，不改变底层任务与执行模型。

**小批次：**任务看板与日历；里程碑、预计投入、简单依赖；提醒频率与静默；Windows 通知与可选开机启动；按实际需要单独验证简易本地服务。

**依赖：**任务模型稳定；运行有关扩展依赖 P3。

**交付物：**共享任务数据的多视图、通知能力。

**验收：**各视图修改一致；拖动日历不改变截止日期或运行规则；系统通知关闭后，核心功能仍可用。

**主要风险与边界：**通知 SDK 和打包增加依赖、日历组件过度设计。Windows 官方当前建议 WPF 等桌面应用使用 Windows App SDK 的 `AppNotificationManager`，应在这个阶段单独验证，而不是阻塞 P1。[Windows 通知文档](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/)

## P5：指定范围的发现与审核入库

**目标：**减少批量整理成本，同时维持人工控制。

**小批次：**扫描边界与排除；基础标识文件解析；候选与依据；重复识别；字段差异审核；重复扫描测试。

**依赖：**P1 的来源和正式项目模型；不依赖 AI。

**交付物：**只读扫描器、候选审核页、扫描报告。

**验收：**重复扫描不重复建项目；人工修正不被覆盖；扫描不执行、不写原项目；权限不足和超限都有说明。

**主要风险与边界：**误识别项目边界、符号链接越界、重复候选。第一批只解析少量常见标识与 README，不追求识别所有开发生态。

## P6：对话处理与可选智能增强

**目标：**把对话变成可关联、可追溯的资料。

**小批次：**文本副本导入；选段与手工摘要；针对真实样本增加格式适配；摘要候选审核；最后才考虑显式授权的 AI 辅助。

**依赖：**P5 的候选与依据机制，以及附件备份。

**交付物：**支持清单明确的导入器；不支持格式时的手工退路。

**验收：**未知格式可以原文件关联；摘要能追溯到原文；拒绝联网仍能使用全部核心功能。

**主要风险与边界：**格式变化、超大导出、提示注入、敏感信息泄露。不接管在线聊天历史，不默认上传全文，不自动把模型建议变成运行配置。

## P7：手机与 Outlook 扩展

**目标：**在不破坏本地优先及公司数据边界的前提下，增加查看便利。

先考虑选定个人任务的只读清单或日程导出，再讨论实时同步。静态导出不能宣传成实时同步。

Outlook 先确认客户端类型、租户策略和授权条件。不能把经典 Outlook 的扩展方式当成所有版本通用；微软明确说明新 Outlook 不支持 COM/VSTO 加载项。若 Graph 路线获得允许，优先评估足够完成任务的最小只读权限，例如 `Calendars.ReadBasic`，而不是上来申请读写日历。[新 Outlook 扩展说明](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/one-outlook)

**公司账号不能在 iPhone 使用，不意味着可以把公司日历自动转存个人账号。**包括忙闲信息在内的传输，也应先确认允许范围。

这一阶段的边界是只读接入和明确授权的数据传输，不做远程执行，不绕过公司限制。

**阶段顺序可以有限调整：**P4 和 P5 可依据实际使用反馈互换，但不能因此推迟 P2、P3。

# 9. 验收与性能验证

## 9.1 功能与安全验收

| 用例 | 必须观察到的结果 | 阶段 |
|---|---|---|
| 昨天记录一个未完成项目，今天重启软件 | 能看到上次完成、阻塞、下一步和应打开的来源 | P1 |
| 输入“采集”“报告”“网页 截图” | 命中预先准备的中文样例；解释命中字段 | P1 |
| 只填写项目名称，关联一份对话或只有想法 | 可以保存，不要求代码目录或仓库 | P1 |
| 项目设置为仅记录 | 不出现可执行的运行按钮，不被扫描改变策略 | P1、P5 |
| 关联路径被移动或删除 | 显示失效来源和修复入口，不丢掉档案 | P1 |
| 打开脚本类型来源 | 只读查看或打开所在目录，不能通过文档动作直接运行 | P1 |
| 同一入口连续点击十次运行 | 只产生一个实际运行，不无意排队十份 | P2 |
| 参数包含中文、空格、引号、`&` 等字符 | 测试程序收到预期参数，不被当成 Shell 操作符 | P2 |
| 程序报错、超时、生成子进程 | 状态、退出码、停止结果和原因可见，没有已知受管进程残留 | P2 |
| 程序大量输出且同时写错误流 | 不死锁、不无限涨内存，日志截断有说明 | P2 |
| 在启动前后及结果提交前模拟崩溃 | 重启后不假装成功，不自动重跑；不确定结果明确标记 | P2、P3 |
| 到提醒时间但不确认 | 没有目标进程启动 | P3 |
| 电脑离线期间错过二十次触发 | 不批量补跑；最多出现一条汇总待处理信息 | P3 |
| 规则暂停或模式切换时已有队列 | 旧队列按约定取消，不能借旧授权启动 | P3 |
| 修改入口、参数、工作目录或凭据版本 | 自动授权失效，需重新确认 | P3 |
| 重复扫描同一目录 | 正式项目数量不会不断增加，拒绝决定被保留 | P5 |
| 手工改名后重新扫描 | 只提出差异建议，不覆盖人工名称 | P5 |
| README 含执行命令、目录中含配置脚本 | 没有任何相关程序被执行，原文件内容不变 | P5 |
| 备份恢复到新目录 | 数据数量、关联、附件校验通过；自动规则保持暂停 | P1 及以后 |
| 备份损坏或磁盘写满 | 明确失败，不覆盖原数据库，不生成“成功备份” | P1 及以后 |
| 删除程序目录或卸载 | 管理数据和外部项目源码仍存在 | 每个分发版本 |

扫描测试还应包含：依赖目录、超大文件、权限不足、循环符号链接、一个目录多个项目、一个项目多个目录、Git 工作树及不支持的对话格式。

## 9.2 扫描器的具体约束

P5 建议初始上限：有限目录深度、最多约 20,000 个目录项、只读取允许的元数据文件、小文件大小上限，以及 README 的有限前缀。具体数值在试用后调整，但上限必须存在。

默认跳过虚拟环境、依赖、构建产物、缓存、版本库对象、工具自己的数据目录，不跟随重解析点跨出指定范围。

读取 Git 信息优先只读解析必要元数据，不执行 Git 命令。仓库地址只是重复线索：同一个仓库可能有多个子项目，不能据此直接合并。

候选身份应考虑规范化路径、项目子位置和来源标识；内容变化生成新版本提议，而不是不断新建项目。人工接受、拒绝和字段修改都要被保留。

## 9.3 性能目标与测量方式

以下都是**验收目标，尚未实测**。基准环境先记录真实 Windows 版本、CPU、内存、SSD、杀毒软件及应用版本，不通过关闭安全软件制造好成绩。

建议使用 50、500、2,000 个合成项目，并在较大样本中加入约 10,000 条任务和一定数量工作记录。

| 指标 | 初始目标 | 测量方式 |
|---|---|---|
| 真正冷启动 | 系统重启后的首次启动约 4 秒内可操作 | 至少 5 次，记录中位数与最大值；不把进程重启冒充冷启动 |
| 普通再次启动 | 约 2 秒内可操作 | 独立进程重复 20 次，记录 P95 |
| 空闲内存 | P1 自身 Private Bytes 目标不超过 150 MiB | 静置 10 分钟；工作集另记，不混用指标 |
| 空闲 CPU | 平均占整机 CPU 目标低于 0.2% | 用进程 CPU 时间增量计算；无扫描、无业务任务 |
| 检索 | 2,000 项目下查询 P95 约 200 毫秒内，输入至结果约 400 毫秒内 | 固定中文测试集，包含短词、多词和无结果 |
| 扫描 | 固定 SSD 样例中，10,000 个目录项、有限元数据读取约 10 秒内；取消约 1 秒内响应 | 固定样例与读取总量，记录排除项；不能只报“每秒多少文件” |
| 应用界面 | 扫描、备份、输出日志时仍可操作 | 测量主要交互延迟，观察是否长时间卡住 |
| 发布体积 | 自包含程序目录先以 250 MiB 为预算目标 | 分别记录压缩包、解压目录与用户数据大小 |
| 调度准确性 | 电脑清醒且应用正常运行时，通常在到期后数秒内响应 | 使用真实时间和测试时钟分别验证；不承诺硬实时 |

必须分开记录：

**开发环境资源**：SDK、IDE、编译和 AI 工具的消耗。  
**工作台自身资源**：主进程及其必须组件。  
**被管理程序资源**：Python、浏览器、采集脚本、本地服务等。

不能把一个采集脚本启动的浏览器内存算成工作台“空闲内存”，也不能把工作台启动的必要辅助进程藏在统计之外。

空闲优化优先使用“下一次到期定时器＋系统恢复事件＋低频校正”，不做每秒全表轮询，不监控全部项目目录，不持续扫描或建立 AI 索引。

## 10.2 每轮开发的工作单位

一轮以**一个能检查的行为变化**为单位，例如“只有名称也能登记项目并在重启后读取”，而不是“完成项目管理模块”。

每轮同时包含必要测试、迁移和交接。新增依赖、修改数据库权威来源、改变权限边界、切换框架，都不能混在普通功能提交中悄悄完成。

运行测试使用专门测试目录和无害测试程序，不拿真实源码、生产数据库或有外部副作用的脚本当夹具。

AI 环境能够生成代码，不等于能够完成 Windows 验收。WPF 启动、Job Object、托盘和通知必须在 Windows 环境实际验证；未执行就标记待验证，不能写“应该没问题”并视为通过。
